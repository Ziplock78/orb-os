Most severe finding

A Studio control can make the real Orb show fake airplanes, and nothing on the dial says so

The Flight Tracker panel has a plain, labeled toggle: Traffic: Live / Test. Switching it to Test and installing puts eight fabricated aircraft (SIM000 through SIM007) on the physical device, drawn through the exact same code path as real contacts. The toggle's own hint text calls this "useful for judging a design... without waiting to see what happens to be overhead," which reads as a preview-time convenience. It is not preview-time. It installs.

There is no build guard. main.cpp's simulated branch compiles into the real firmware unconditionally (platformio.ini excludes only four desktop-only files by name, and main.cpp is not one of them), and theme_style.cpp:482 parses the flag with no restriction. Once installed, the dial gives no indication anywhere that what it is showing is not real. This is the one finding in this audit that contradicts the Orb's entire premise, not just a principle within it.

Detail

Findings, principle by principle

Each finding cites the file and line it was verified against, and whether the number came from reading the source or from the device running live.

P1

Evenness before rate

Fail

Charter requirement: interval spread ≤ 15% of mean (T1), mean ≤ 120 ms (T2).

Live device, Steam Punk theme, Flight Tracker, 24 Aug 2026, 75 s / 5 windows

mean 239 ms (budget 120 ms) · spread 78% of mean (budget 15%) · worst single interval 408 ms.

The EMA smoothing itself is sound: measured at boot, before aircraft populate the scope, the same device holds 100/102/105 ms, spread 5 ms, comfortably inside both budgets. The failure is not the pacing algorithm. It is the per-frame compositing cost once the full scene is live: a 489×489 sweep sprite whose actual ink is an 86×272 hand, rotated in full every frame.

A fix for exactly this (trimming the sprite to its ink, carrying the pivot with it) was built and unit-tested this session, and its geometry was confirmed correct in the desktop simulator at 0° and 90°. It is not yet validated on the device: an earlier attempt to push it over the serial cable silently failed because the firmware serves themes from a baked flash partition ahead of the SD card, and the improvement briefly reported from that attempt was invalid for the same reason (see Covenant C6 in the charter, which this incident is the receipt for). A live layer-cost pass run before that discovery also found that switching aircraft, glass, and static art off individually did not reduce the frame cost, which means a second, still-unidentified driver is contributing roughly as much as the sprite was.

Fails today. A real fix is in flight but unconfirmed, and it will not close the gap alone.

P2

The instrument never blames itself for the world

Pass

Charter requirement: every status string maps to one observed fact.

radar_view.cpp:2754-2793, setFeedStatus()

The banner shows "No aircraft data" gated purely on elapsed time since the last successful poll, nothing else. The function's own comment documents the incident this replaced: a banner that said "WiFi is fine, the service is not answering" while the service in fact answered a laptop in 1.3 s and the Orb was unreachable. The fix is now load-bearing in the code itself: "STATE ONLY, NEVER A CAUSE."

The one HTTP-refusal message that does name a cause (main.cpp:414, "the service is refusing requests") is gated on an actually-observed 4xx status code, not inferred, so it holds to the same standard.

Passes. This is the principle the team paid most dearly to learn, and it shows.

P3

Silence is a claim

Fail

Charter requirement: contacts dim at 60 s, outline at 120 s, earn an advisory at 180 s (T4).

aircraft.h:26, adsb_client.cpp:351, main.cpp:361

Aircraft.lastUpdateMs is declared // millis() when we last saw it (for trails/expiry) and is written on every ingest. It is never read anywhere outside ingest. There is no expiry logic and no staleness-driven dimming for individual contacts.

An aircraft's presence on the dial today is binary: it is drawn at full fidelity if this poll's response contained it, and it vanishes without any transition the instant one poll misses it. ADS-B position reports gap routinely, so this reads as flicker rather than as the graduated staleness the charter specifies.

Fails. The field the mechanism needs already exists and is already populated. Nothing reads it.

P4

One voice, never an alarm

Pass

Charter requirement: at most one advisory, lowest in the hierarchy, never modal.

radar_view.cpp, s_feedWarn (banner) and s_loading (loading screen)

Exactly one banner-class element exists on the flight radar screen. It and the loading screen are explicitly mutually exclusive (if (s_loadingPending) { show(s_feedWarn, false); return; }). Nothing modal, nothing that blocks the dial.

Worth noting for completeness: the HUD signal-bars icon (ui.cpp:297) also turns amber on a stale feed, ambient chrome rather than an advisory, comparable to a battery icon, so it does not count as a second voice under the charter's own definition. It does mean the same fact is expressed twice at once, once as icon color and once as banner text, which is harmless but worth being deliberate about.

Passes.

P5

An empty sky is a valid reading

Pass

Charter requirement: zero aircraft in range must look like a healthy instrument.

main.cpp:374, snapshot_gate.h

g_lastFeedOkMs, the clock the advisory banner reads, updates on any successful poll, including one that returns zero aircraft. A steady-state empty sky with a healthy feed never trips "No aircraft data": the message is genuinely about feed silence, not sky silence.

One edge case sits outside this: on a true cold boot into a durably empty sky, AircraftSnapshotGate withholds the very first empty result (to prevent one flickered blank poll from clearing real contacts) and only publishes once AC_STALE_MS (15 s) has passed since the first empty poll, which at a 10 s poll interval takes roughly two cycles. Worst case the loading screen can sit for 20-30 s before showing a correctly empty, healthy dial. The charter has no timing budget covering this specific case, which is a gap in the charter as written, not only in the code.

Passes in steady state. The charter should get a budget for first-boot-into-empty-sky; see the punch list.

P6

The tool cannot promise what the device cannot deliver

Pass

Charter requirement: refuse an install on a capability mismatch, never warn and proceed.

orb-caps.ts:1-15, studio.tsx:3366

The design rule is stated in the code's own comment ("The rule Studio follows is refuse, not warn. A warning that is dismissed leaves exactly the state we are trying to make impossible") and it is genuinely enforced: disabled={installing || !isSupported()} hard-disables the install button, not a dismissible banner beside an active one.

One gap in the evidence, not the behavior: the charter's proof clause calls for "preview parity captures rendered from the same theme through both paths." That capability exists (--themeshot, used manually in this session) but is not wired into any automated check. Parity is provable on demand, not continuously proven.

Passes. The one gap is in how the guarantee is verified over time, not in whether it holds today.

P7

A design choice carries its cost at authoring time

Partial

Charter requirement: Studio states a cost, in the user's units, while the choice is being made.

theme-forge.ts:2058-2135 (planSweepTrim, bakeSweepSprite); studio.tsx:2230

The backend half is real: every rotating sweep sprite is now trimmed to its opaque bounds at bake time, with a regression test asserting the pivot travels with the crop so no pixel moves. This is a genuine, tested fix for the exact defect that cost two days this week.

The front-end half the charter calls for does not exist. bakeSweepSprite's result (how much was trimmed, what it will now cost) is consumed only inside the export pipeline and never reaches the panel. The single cost-adjacent line in the entire Flight Tracker panel is a hint on trail steps that explicitly punts the estimate to the user: "watch the dial rather than the number." A user uploading an oversized sweep image today gets a silently-corrected result with no visibility into what happened or why.

Partial. The device is protected from the mistake. The person authoring it is never told the mistake was there.

P8

What the design says, the device does exactly

Pass

Charter requirement: authored values are promises, honored literally or refused.

radar_view.cpp:1299-1345 (applyRadarLayerOrder); live device, 24 Aug 2026

Layer-kind numbering matches exactly between firmware and Studio (0 sweep, 1 aircraft, 2 info card, 3/4 static art, 5 wash, confirmed on both sides). The card fix from earlier this week (plate, card, and text now move as one unit) ships a self-check that reads LVGL's actual sibling order back and prints it, rather than trusting the order array alone.

Cap fidelity was confirmed live in the same session as this audit: [acdbg] feed=12 inRange=10 flying=10 drawn=7 cap=7. The authored cap and the device's own report of what it drew match exactly, and the ceiling both sides clamp against (MAX_AIRCRAFT in Studio, ADSB_MAX_AIRCRAFT in firmware) is the identical value, 12, on both sides, so there is no silent divergence possible through the normal UI.

Passes, with live confirmation, not just code review.

P9

Nothing on the dial is invented

Fail

Charter requirement: every contact is real; no demo data in shipping firmware; no dependence on a single feed provider.

studio.tsx:2995-3003; main.cpp:314-364; theme_style.cpp:482; platformio.ini build_src_filter

Covered in full above. The Traffic Live/Test toggle is a plain, labeled, always-available control, not a hidden or legacy field, and the device-side code that honors it compiles into every production build with no guard.

config.h:84-91

Separately: the code openly documents that it is "genuinely single-sourced." adsb.lol is the only reachable provider because the board cannot do TLS at all and every alternative provider is either HTTPS-only or actively refusing requests. This is a disclosed, understood constraint with a real cause, not an oversight, but it still means a whole category of aircraft can disappear if that one provider has a bad day, which is exactly what the charter's forbid clause names.

Fails, on both counts. The synthetic-traffic path is the more serious of the two and should be treated as urgent.

Action

What to fix, in order

1
Close or gate the Test traffic path before it ships to anyone else.

Either remove synthetic traffic from the device build entirely and keep it simulator-only, or force an unmissable, permanent on-screen mark whenever simulate is active. This is the one finding that breaks the Orb's core promise.

P9 · main.cpp:314, studio.tsx:2995

2
Reinstall Steam Punk to actually load the sweep trim, then find the second cost driver.

The trim is built and geometrically verified but not yet confirmed on-device. Even if it lands cleanly, the layer-pricing pass showed something else is costing roughly as much per frame and it was never identified.

P1 / T1 / T2 · radar_view.cpp sweep_timer_cb

3
Build per-contact staleness dimming.

The data the mechanism needs already exists and is already correct. This is wiring, not discovery: read lastUpdateMs against three thresholds and scale opacity or switch to an outline style.

P3 / T4 · aircraft.h:26

4
Replace the static "Loading aircraft and location data" text with a determinate line.

Name the actual step (waiting on position fix, waiting on first poll, elapsed time), so a slow boot reads as progress rather than as a hang. This is the literal complaint raised earlier tonight.

S1 · radar_view.cpp:1445

5
Surface the sweep trim's result in the panel.

Even a single line, "trimmed an oversized sweep image, no visual change," turns a silent correction into the authoring-time signal P7 actually asks for.

P7 · theme-forge.ts:2129

6
Scope a plain-HTTP aggregator gateway.

The device cannot do TLS, full stop, so real multi-source failover has to live off-device. This is infrastructure, not firmware, and is already precisely diagnosed in the code's own comments.
